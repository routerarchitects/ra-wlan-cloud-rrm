# Internal Wi-Fi management APIs

These APIs reuse RRM's synchronized device topology, layered `DeviceConfig`,
configuration manager, Cloud SDK client, and Kafka scan ingestion. No Mango MCP
code changes are included here.

## Authentication and MCP integration

All three endpoints require the **private/internal RRM listener** and both
`X-INTERNAL-NAME` and `X-API-KEY`, using the existing inter-service credential
generated by `Utils.generateServiceKey(serviceConfig)`. Use the deployment's
service credential provisioning; do not send an end-user bearer token as an
internal service key. These routes enforce internal authentication even when
`useOpenWifiAuth` is false. Public listener access is rejected, including valid
user tokens, service keys, and spoofed forwarding headers.

MCP must validate the caller, resolve device ownership, and enforce the project's
adopted OWPROV device authorization policy **before** calling RRM. Configuration
operations require the approved configuration/device-operation permission;
scan execution requires authorized device execution; results require the approved
inventory/telemetry read permission. RRM does not introduce OWPROV resource names
or perform tenant permission evaluation on behalf of MCP. Possession of an RRM
service key is not proof of an end user's permission to access a device.

Resolve RRM through existing Kafka discovery and use its private endpoint.
Serial numbers must identify a device in RRM's synchronized topology and contain
1–64 ASCII letters, digits, hyphens, or underscores.

| MCP tool | MCP inputs | RRM request |
| --- | --- | --- |
| `optimize_2g_bandwidth` | `router_id`, `bandwidth_value` | `PUT /api/v1/device/{router_id}/wifi/bandwidth`, body `{"band":"2g","bandwidth":"HT20"}` or `HT40` |
| `gw_wifi_scan_run` | `router_id` | `POST /api/v1/device/{router_id}/wifiScan`, no body |
| `gw_wifi_scan_result` | `router_id` | `GET /api/v1/device/{router_id}/wifiScanResults`, no body |

## Manual 2.4 GHz bandwidth

```http
PUT /api/v1/device/dc62796520cd/wifi/bandwidth
Content-Type: application/json

{"band":"2g","bandwidth":"HT40"}
```

`HT20` and `HT40` are case-sensitive and map to numeric `channel-width` values
20 and 40 MHz in the OpenWiFi radio configuration. This is a manual selection;
it runs no optimizer and does not select a width automatically.

Validation requires:

- An online gateway in both the RRM topology and OWGW inventory.
- Enabled global `configManagerParams.configEnabled`, effective `enableConfig`,
  and effective `enableRRM` (the existing configuration pipeline requires RRM).
- Exactly one configured `2G` radio and one matching device capability PHY.
- The requested width in effective `allowedChannelWidths["2G"]`, if specified,
  and an advertised `HT`/`VHT`/`HE`/`EHT` mode for that width in `htmode`.
- Available capability channel data and a radio country matching the capability
  country. The effective primary channel must be in that regulatory channel
  list; HT40 additionally requires an available secondary channel four channel
  numbers above or below, within channels 1–13. With `channel: "auto"`, all
  configured `valid-channels` (or capability channels when absent) are checked.

Devices with missing or ambiguous capabilities are rejected. These checks use
the available device regulatory channel data; the AP/driver remains responsible
for final regulatory and 20/40 coexistence enforcement. No secondary channel is
chosen by RRM. Vendor-specific restrictions absent from capabilities cannot be
validated here.

RRM persists `userChannelWidths["2G"]` in the AP configuration layer using the
existing configuration file mechanism. This property is separate from the
`allowedChannelWidths` constraint. It inherits through default, network, zone,
and AP layers with the existing whole-field map replacement semantics. The API
preserves other effective band entries when creating an AP override. Removing
the override through the existing layer APIs restores inheritance; absent any
width override, the existing configured width is preserved.

Only the `2G` width is changed. Existing channel and power settings continue
through their existing precedence rules. A width request does not assign a
5 GHz width, channel, or transmit power.

After persistence, a changed width queues its RF zone for the existing
configuration evaluation/delivery pipeline. The response is HTTP **202**:

```json
{"success":true,"message":"Wi-Fi bandwidth config command accepted"}
```

This acknowledges persisted intent and queued evaluation, **not device
application**. The existing zone evaluation can also deliver other pending RRM
settings. Debounce-delayed updates and failed OWGW configuration commands remain
queued for subsequent evaluation. If the gateway disconnects after acceptance,
the queued zone is retained for a later connected evaluation. Requests made
while offline are rejected without storing a new selection.

If the requested width already equals the OWGW configured radio width, RRM
stores the explicit override and returns HTTP **200** without adding an update:

```json
{"success":true,"message":"Wi-Fi bandwidth already configured; user override accepted"}
```

Previously queued changes still undergo normal evaluation. Neither status
confirms the device's operating width. A later delivery failure is logged and
retried; it cannot change a previously returned HTTP acknowledgment.

## Trigger a scan

`POST /api/v1/device/{serialNumber}/wifiScan` calls the managed
`UCentralClient.wifiScan(serialNumber, false)` exactly once. It requires an online
gateway in both inventories and `enableRRM` so the existing modeler can ingest
the results. `enableWifiScan` controls **automatic scheduling only** and does not
disable this explicit manual operation.

HTTP **202**:

```json
{"success":true,"message":"Channel scan started"}
```

RRM validates command identity, submission/execution metadata, status and error
codes, including embedded result errors. Null, empty, mismatched, rejected, and
failed acknowledgments are failures. This response acknowledges command
acceptance and returns no scan results. The existing SDK/OWGW command protocol
may wait for an AP command response up to its configured socket timeout; RRM adds
no polling/wait for Kafka ingestion. Some OWGW versions return the acknowledgment
after command completion, but this API still makes no completion guarantee.

OWGW publishes successful scan result events to Kafka's configured `wifiscan`
topic. RRM's existing consumer and modeler parse those events. Fetch results
separately. Do not automatically retry scan requests after an uncertain timeout:
the first request may already have reached the device.

## Read the latest complete scan

`GET /api/v1/device/{serialNumber}/wifiScanResults` returns HTTP **200** with
exactly these fields:

```json
{
  "timestamp": "2026-07-09T06:00:00Z",
  "networks": [
    {
      "ssid": "ExampleSSID",
      "bssid": "AA:BB:CC:DD:EE:FF",
      "channel": 6,
      "signal": -55,
      "encryption": "WPA2"
    }
  ]
}
```

The endpoint reads only the specified device. It returns all entries in the
most recently **received complete event**, without merging scan rounds. Signal
is in dBm. Timestamp is the Kafka event timestamp in UTC ISO 8601, never
`last_seen` and never the HTTP request time. An empty completed scan is valid:

```json
{"timestamp":"2026-07-09T06:00:00Z","networks":[]}
```

Malformed entry batches do not replace the previous good batch. Malformed
security information produces `UNKNOWN` without discarding otherwise valid scan
entries. Snapshots are published atomically and copied for concurrent API reads.
The optimizer's existing bounded scan history and parsed information elements
are preserved. Scan state is in memory and is cleared on restart, topology
removal, or RRM disablement; no database is added.

Unknown devices return **404** `Device not found`. Known devices without scan
history return **404** `No scan history for device`. Stale scans are returned with
their original timestamp, with no age cutoff and no extra public metadata. MCP
must compare timestamps against its own freshness policy. A scan request does
not clear history or prove the next read belongs to that request.

### Security mode (`encryption`)

This field describes the Wi-Fi security mode, not just the cipher.

| Value | Evidence |
| --- | --- |
| `OPEN` | Explicit clear privacy capability and a valid available IE array without security advertisements. |
| `WEP` | Privacy enabled and explicit legacy Shared Key Challenge Text IE evidence (128-byte challenge), without RSN/WPA. Ordinary privacy-only scan entries remain `UNKNOWN`. |
| `WPA` | Explicit Microsoft WPA/WME vendor IE of WPA type/version, with supported AKM and cipher suites. WMM/WPS and arbitrary vendor IEs do not imply WPA. |
| `WPA2` | RSN version 1, recognized PSK/SHA256/FT or 802.1X AKMs with valid group and pairwise cipher suites. |
| `WPA3` | SAE/FT-SAE with strong ciphers and PMF capable+required; unambiguous Suite-B-192 AKM requires GCMP-256 and PMF. |
| `WPA2/WPA3` | Supported PSK-family and SAE-family AKMs, strong ciphers, PMF capable. |
| `UNKNOWN` | Missing, malformed, contradictory, unsupported, or ambiguous security information, including unknown AKMs alongside PSK. |

WPA2 is not inferred from AES alone. Numeric AKM selectors are decoded when
preserved. The decoded OWGW RSN field names are supported, including its use of
`Group Cipher Suite` keys inside the pairwise list. An OWGW decoder that replaces
an unrecognized suite with `unknown` and discards the original selector cannot
be reliably classified as WPA3. Raw-only/undecoded RSN IEs, OWE, and incomplete
legacy WPA decodings return `UNKNOWN`. Incoming `encryption` values are ignored
and replaced by the derived classification. No internal IEs, frequency,
capabilities, or other model fields appear in the public result.

## Errors

All new-route errors use JSON:

```json
{"error":"Device is offline"}
```

| HTTP status | Meaning |
| --- | --- |
| 400 | Invalid serial, malformed JSON, wrong band, or bandwidth other than HT20/HT40. |
| 403 | Public listener access or missing/invalid internal service credentials. |
| 404 | Unknown device, missing OWGW device, or no scan history (distinguished by `error`). |
| 409 | Offline gateway, disabled configuration updates, or disabled RRM. |
| 422 | Missing/unsupported radio capabilities, disallowed width, or regulatory/channel incompatibility. |
| 500 | Bandwidth persistence/queueing failed; acceptance was not returned. |
| 502 | OWGW request failed, rejected the command, or returned a null/malformed/mismatched acknowledgment. |
| 503 | OWGW inventory could not be fetched. |
| 504 | Recognized OWGW/socket timeout; command acceptance may be unknown. |

The existing SDK returns `null` for downstream non-success HTTP responses or
deserialization failures, so those cases are reported as 502 rather than
inventing a more precise downstream status. Raw device errors and credentials
are not echoed to callers.

## curl examples

Set `RRM_PRIVATE_URL` to the discovered private RRM API base (without `/api/v1`),
and set `RRM_INTERNAL_NAME` and `RRM_SERVICE_KEY` through the deployment's existing
secret mechanism. Use a device the MCP caller is authorized to manage.

```bash
router_id=dc62796520cd

curl --fail-with-body -X PUT \
  "$RRM_PRIVATE_URL/api/v1/device/$router_id/wifi/bandwidth" \
  -H "X-INTERNAL-NAME: $RRM_INTERNAL_NAME" \
  -H "X-API-KEY: $RRM_SERVICE_KEY" \
  -H 'Content-Type: application/json' \
  --data '{"band":"2g","bandwidth":"HT20"}'

curl --fail-with-body -X POST \
  "$RRM_PRIVATE_URL/api/v1/device/$router_id/wifiScan" \
  -H "X-INTERNAL-NAME: $RRM_INTERNAL_NAME" \
  -H "X-API-KEY: $RRM_SERVICE_KEY"

curl --fail-with-body \
  "$RRM_PRIVATE_URL/api/v1/device/$router_id/wifiScanResults" \
  -H "X-INTERNAL-NAME: $RRM_INTERNAL_NAME" \
  -H "X-API-KEY: $RRM_SERVICE_KEY"
```

Run verification with `mvn test` and `mvn package`. Unit and HTTP tests use a
controllable Cloud SDK client and simulated Kafka records; live OWGW, Kafka, and
physical AP validation still require a deployment.
